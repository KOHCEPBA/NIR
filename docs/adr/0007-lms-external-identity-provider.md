# ADR-0007: LMS как внешний провайдер идентификации

**Date**: 2026-05-20
**Status**: accepted
**Deciders**: автор проекта, проектная команда

## Context

У ВУЗа есть единая LMS для авторизации. Система должна использовать существующие учетные записи, но сохранять собственные роли и доменные права доступа.

## Decision

Интегрировать аутентификацию с LMS через адаптер внешнего identity provider внутри Identity. Identity работает с LMS напрямую, связывает внешний subject с внутренним пользователем, назначает прикладные роли и формирует доверенный authorization context для прикладных модулей. Подписанный межпроцессный контекст потребуется только для выделенных сервисов. Integration не участвует в authentication path; конкретный протокол уточняется после обследования LMS.

## Alternatives Considered

### Собственные логины и пароли

- **Pros**: независимость от LMS.
- **Cons**: дублирование учетных записей и дополнительная ответственность за credentials.
- **Why not**: противоречит единой системе входа ВУЗа.

### Полное управление ролями только в LMS

- **Pros**: единый источник учетных данных и ролей.
- **Cons**: LMS может не знать специфические права учебных планов.
- **Why not**: прикладная авторизация должна оставаться в системе.

## Consequences

### Positive

- Единый вход и отсутствие локальных паролей.
- Адаптер изолирует систему от конкретного протокола LMS.

### Negative

- Доступность входа зависит от внешней системы.
- Требуется синхронизация профиля и жизненного цикла пользователя.

### Risks

- Неизвестный протокол LMS; до интеграции проводится обследование, предпочтительным вариантом считается OIDC Authorization Code с PKCE.
