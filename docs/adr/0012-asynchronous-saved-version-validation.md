# ADR-0012: Асинхронная валидация сохраненной версии

**Date**: 2026-06-16
**Status**: accepted
**Deciders**: автор проекта, проектная команда

## Context

Сохранение immutable version не должно зависеть от времени выполнения Validation. При этом согласование разрешено только для проверенного snapshot, а пользователь должен видеть технический статус и результат проверки. Для быстрой обратной связи рабочая ревизия отдельно поддерживает синхронную промежуточную валидацию.

## Decision

Начиная с Post-MVP 1 сохранять snapshot синхронно со статусом `PENDING` и в той же транзакции создавать задание проверки в DB-backed очереди Versioning. Worker атомарно захватывает доступное задание, выполняет Validation и идемпотентно обновляет статус. Application event после commit может немедленно разбудить worker, но PostgreSQL остается источником истины и обеспечивает восстановление после перезапуска. Статус проходит через `PENDING`, `RUNNING`, `COMPLETED`, `FAILED` или `UNAVAILABLE`; согласование блокируется до `COMPLETED` и при outcome `ERROR`, а `WARNING` требует явного подтверждения.

## Alternatives Considered

### Синхронная проверка при сохранении версии

- **Pros**: пользователь сразу получает окончательный результат, проще последовательность состояний.
- **Cons**: сохранение зависит от Validation и может завершиться timeout при росте числа правил.
- **Why not**: недоступность проверки не должна мешать зафиксировать immutable snapshot.

### Сохранять только версии, прошедшие промежуточную проверку

- **Pros**: не требуется отдельный асинхронный запуск после сохранения.
- **Cons**: рабочая ревизия может измениться между проверкой и созданием snapshot; результат не доказывает корректность сохраненной версии.
- **Why not**: согласование должно опираться на проверку конкретного неизменяемого snapshot.

### Проверять версию только вручную

- **Pros**: меньше фоновых событий и состояний.
- **Cons**: пользователь может забыть запустить проверку, а версия неопределенно долго не готова к согласованию.
- **Why not**: автоматический запуск дает предсказуемый workflow.

## Consequences

### Positive

- Версия сохраняется независимо от результата фоновой Validation.
- Результат однозначно относится к конкретному immutable snapshot.
- Набор правил может расти без увеличения timeout команды сохранения.

### Negative

- Пользователь некоторое время видит незавершенный статус.
- Требуются таблица заданий, worker, retry с backoff, timeout и ручной replay.
- Workflow должен учитывать технический status и outcome.

### Risks

- Версия может застрять в `PENDING` или `RUNNING`; по истечении технического timeout она переводится в `UNAVAILABLE`, а оператор может выполнить replay.
- Задание может обрабатываться повторно после истечения lease; обработчик использует идемпотентные переходы статусов и уникальный business key версии.
- Очередь может расти при замедлении Validation; контролируются возраст старейшего задания, число retry и длительность обработки.
