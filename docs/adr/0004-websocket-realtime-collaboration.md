# ADR-0004: WebSocket для совместного редактирования

**Date**: 2026-04-30
**Status**: accepted
**Deciders**: автор проекта, проектная команда

## Context

Пользователи должны видеть активных участников и изменения структурированных сущностей плана в реальном времени. Для MVP не нужны курсоры и совместное редактирование свободного текста.

## Decision

Использовать WebSocket для presence и live-доставки подтвержденных изменений. Постоянное состояние изменяется только через Curriculum с optimistic locking. При одном экземпляре backend краткоживущий presence может храниться в памяти; перед горизонтальным масштабированием он переносится в Redis.

## Alternatives Considered

### Периодический polling

- **Pros**: простая серверная модель.
- **Cons**: задержки, лишние запросы и слабый UX совместной работы.
- **Why not**: не выполняет real-time требование должным образом.

### Server-Sent Events

- **Pros**: простая доставка событий от сервера к клиенту.
- **Cons**: канал однонаправленный, команды потребуют отдельного транспорта.
- **Why not**: WebSocket удобнее для двусторонней сессии редактора.

## Consequences

### Positive

- Низкая задержка обновлений и единый двусторонний канал.
- Возможность позднее выделить Collaboration для независимого масштабирования WebSocket-нагрузки.

### Negative

- Нужны reconnect, heartbeat и восстановление пропущенного состояния.
- Прокси и балансировщик должны поддерживать долгоживущие соединения.
- Presence в памяти теряется при перезапуске, что допустимо: клиенты повторно регистрируются после reconnect.

### Risks

- Потеря или изменение порядка сообщений; клиент сверяет ревизии и при разрыве повторно получает актуальное состояние через REST.
