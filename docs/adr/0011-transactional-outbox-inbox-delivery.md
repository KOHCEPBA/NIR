# ADR-0011: Transactional outbox/inbox для доставки событий

**Date**: 2026-06-14
**Status**: proposed
**Deciders**: автор проекта, проектная команда

## Context

Если Kafka или другой внешний брокер будет принят, изменение доменных данных в PostgreSQL и публикация события не образуют общей атомарной транзакции. Для текущих внутрипроцессных взаимодействий эта проблема отсутствует; долговечность фоновых задач определяется отдельно.

## Decision

При принятии внешнего брокера использовать transactional outbox у producers и transactional inbox у consumers, если событие нельзя безопасно восстановить из другого долговечного источника. Параметры polling, retry и DLT определяются для конкретного сценария. Внутрипроцессные события модульного монолита не требуют outbox/inbox.

## Alternatives Considered

### Прямая запись в БД и Kafka

- **Pros**: минимальный объем кода и таблиц, низкая задержка публикации.
- **Cons**: dual-write race приводит к потере события или несогласованному состоянию.
- **Why not**: нарушает требование надежной доставки изменений через границу процесса.

### Распределенная транзакция

- **Pros**: единая атомарность записи данных и сообщения.
- **Cons**: высокая связанность, сложная эксплуатация и отсутствие практичной общей XA-транзакции PostgreSQL/Kafka для выбранного стека.
- **Why not**: сложность и ограничения превышают потребности MVP.

### Полагаться на Kafka exactly-once semantics

- **Pros**: уменьшает число дубликатов внутри Kafka pipeline.
- **Cons**: не обеспечивает атомарность между Kafka и произвольными изменениями PostgreSQL у producer/consumer.
- **Why not**: не закрывает основную границу согласованности системы.

### Публикация Kafka только из `afterCommit`

- **Pros**: низкая задержка и отсутствие таблицы outbox.
- **Cons**: падение процесса после commit БД, но до broker acknowledgement безвозвратно теряет событие.
- **Why not**: callback не является долговечным механизмом доставки; он допустим только как сигнал ускорения outbox publisher.

## Consequences

### Positive

- Зафиксированное бизнес-изменение не теряет предназначенное для Kafka событие.
- Повторная доставка не создает повторный side effect.
- DLT и ручной replay позволяют восстанавливать обработку после исправления причины.

### Negative

- Каждый Kafka producer/consumer содержит необходимые outbox/inbox tables, publisher и очистку обработанных записей.
- Состояние между отдельными процессами остается eventually consistent.
- Возраст outbox, consumer lag, retry и DLT требуют мониторинга.

### Risks

- Ошибка реализации inbox может допустить повторный side effect; уникальный `event_id` и изменение доменных данных фиксируются одной транзакцией.
- Outbox может бесконтрольно расти; вводятся retention, batch cleanup и метрика возраста старейшей неопубликованной записи.
- Polling может не выполнить latency target; контролируются commit-to-Kafka и commit-to-consumer percentiles, а при необходимости publisher переводится на CDC без изменения event contract.
