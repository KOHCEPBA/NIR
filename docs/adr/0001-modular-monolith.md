# ADR-0001: Модульный монолит с извлекаемыми модулями

**Date**: 2026-04-23
**Status**: accepted
**Deciders**: автор проекта, проектная команда

## Context

Система охватывает редактирование, совместную работу, проверки, версионирование, согласование, файлы и интеграции. Эти области требуют явных границ ответственности, но для MVP отсутствуют подтвержденные требования к независимому масштабированию и развертыванию каждой области. Микросервисная реализация с первого релиза добавила бы сетевые отказы, распределенные транзакции и значительную эксплуатационную нагрузку до появления соответствующей необходимости.

При этом архитектура должна позволять развивать отдельные области независимо и при необходимости выделять их в отдельные процессы.

## Decision

Реализовать backend как модульный монолит на Java 21 и Spring Boot: один развертываемый процесс с модулями, выделенными по бизнес-возможностям.

Границы модулей обеспечиваются следующими правилами:

- каждый модуль владеет своей доменной моделью и таблицами;
- другой модуль обращается к нему только через публичный application API или опубликованное событие;
- прямой доступ к repository, entity и внутренним пакетам другого модуля запрещен;
- межмодульные зависимости проверяются Spring Modulith и ArchUnit;
- модули реализуются как package-based Spring Modulith modules в одном backend build и одном развертываемом артефакте;
- внешние REST/STOMP-контракты не зависят от способа развертывания модулей;
- локальные взаимодействия выполняются синхронными вызовами application API или внутрипроцессными событиями;
- одна бизнес-транзакция изменяет данные только одного модуля-владельца; межмодульные процессы координируются командами и событиями, а исключение требует отдельного ADR;
- долговечные фоновые задачи хранятся в PostgreSQL в очереди модуля-владельца и выполняются идемпотентными workers;
- Kafka и transactional outbox могут быть введены отдельным принятым решением при появлении подтвержденной границы процесса.

В MVP модули работают с одним экземпляром PostgreSQL. Владение таблицами фиксируется отдельными схемами и миграциями; межмодульные JPA-связи и прямые SQL-запросы запрещены. Выделение модуля в сервис выполняется только при наличии измеримой причины: независимого профиля масштабирования, отдельного цикла поставки, требований изоляции отказов или безопасности либо самостоятельной команды-владельца.

## Alternatives Considered

### Микросервисы с первого релиза

- **Pros**: независимые развертывание, масштабирование и изоляция отказов.
- **Cons**: распределенная согласованность, сетевые ошибки, больше runtime-компонентов, контрактных тестов и эксплуатационных процедур.
- **Why not**: преимущества не подтверждены нагрузкой и организационной структурой MVP, а сложность возникает сразу.

### Монолит без модульных границ

- **Pros**: минимальная начальная стоимость разработки.
- **Cons**: неявное владение данными, сильная связанность и дорогая последующая декомпозиция.
- **Why not**: не обеспечивает требуемую расширяемость и контролируемую эволюцию системы.

## Consequences

### Positive

- MVP разрабатывается, тестируется и развертывается как одно backend-приложение.
- Локальные сценарии не зависят от сети, Kafka и распределенной согласованности.
- Бизнес-границы остаются явными и пригодными для последующего выделения.

### Negative

- Backend масштабируется и выпускается как единое целое, пока модуль не выделен.
- Ошибка процесса может затронуть несколько функций системы.
- Команда должна постоянно контролировать модульные зависимости.
- Межмодульные процессы с несколькими записями требуют явной обработки промежуточных состояний и повторов вместо общей транзакции.

### Risks

- Модульные границы могут размыться из-за прямого доступа к данным; риск снижается автоматическими архитектурными тестами и code review.
- Фоновая задача может выполняться повторно после сбоя; workers проектируются идемпотентными, а зависшие lease возвращаются в очередь.
- Выделение сервиса потребует переноса данных и замены локальных вызовов сетевыми контрактами; это отдельное изменение, а не автоматическая операция.
