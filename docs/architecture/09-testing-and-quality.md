# Стратегия тестирования и качества

## Цель документа

Документ определяет уровни тестирования, правила их запуска и минимальные проверки перед поставкой. Для MVP не устанавливаются формальный процент покрытия и отдельные нагрузочные испытания.

## Принципы

1. Unit- и integration-тесты запускаются независимо друг от друга.
2. Изменение поведения сопровождается тестом на соответствующем уровне.
3. Критическая бизнес-логика проверяется сценариями, а не только процентом покрытия.
4. Тесты воспроизводимы и не зависят от общих внешних стендов.
5. Production-данные не используются в автоматических тестах.
6. Нестабильный тест исправляется или временно изолируется с зарегистрированной задачей; молчаливые повторные запуски не считаются исправлением.

## Уровни тестирования

### Unit-тесты

Unit-тесты выполняются без Spring context, контейнеров, сети и реальной БД. Они проверяют:

- доменные правила и таблицы нормативных ограничений;
- расчет нагрузки и построение температурной карты;
- переходы статусов версий, валидации, импорта и согласования;
- проверку циклов пререквизитов;
- diff сохраненных версий;
- преобразование и нормализацию импортируемых данных;
- авторизационные policy и обработку конфликтов ревизий.

Основной стек: JUnit 5, AssertJ и Mockito только для внешних зависимостей. Доменные объекты предпочтительно тестируются без mock.

### Integration-тесты

Integration-тесты проверяют взаимодействие Spring-компонентов с реальной инфраструктурой через Testcontainers. Контейнер и набор тестов становятся обязательными начиная с релиза, в котором используется соответствующий компонент:

| Компонент | Что проверяется |
|---|---|
| PostgreSQL | SQL, ограничения, транзакции, optimistic locking и миграции |
| DB-backed jobs | конкурентный захват через `SKIP LOCKED`, lease timeout, retry и идемпотентное повторное выполнение |
| Kafka | публикация, consumer groups, retry, inbox/outbox и повторная доставка |
| Redis | presence, TTL и координация real-time соединений |
| Временный volume | лимиты, гарантированное удаление, очистка после рестарта и отсутствие HTTP-доступа |

Внешние системы ВУЗа заменяются управляемыми stub-сервисами. Integration-тесты включают REST security, доступ к объектам по организационному контексту и STOMP CONNECT/SUBSCRIBE.

Unit- и integration-тесты должны иметь разные source sets, build-задачи или профили. Команды конкретного build tool фиксируются при создании backend-проекта. Общий запуск выполняет оба набора последовательно.

Границы модульного монолита дополнительно проверяются Spring Modulith и ArchUnit: запрещаются циклические зависимости, обращение к внутренним пакетам другого модуля и доступ к чужим repository/entity. Для критичных взаимодействий добавляются module integration tests через публичный application API.

### E2E-тесты

Ключевые пользовательские сценарии проверяются Playwright в браузере против развернутой среды `dev`. Сценарий включается в обязательный набор начиная с релиза, в котором появляется соответствующая функция:

1. вход через тестовый identity provider и проверка ролей;
2. создание или импорт учебного плана;
3. `[Post-MVP 1]` редактирование с обновлением второго клиента через STOMP;
4. `[Post-MVP 1]` конфликт параллельных изменений и REST resync после разрыва WebSocket;
5. промежуточная валидация рабочей ревизии;
6. сохранение версии и получение результата проверки;
7. `[Post-MVP 2]` запуск и прохождение согласования;
8. экспорт и получение сформированного файла;
9. `[Post-MVP 1]` импорт через staging.

E2E-набор содержит короткий smoke-поднабор для проверки развертывания. Перед выпуском в `production` запускаются все сценарии, относящиеся к текущему релизу; post-MVP сценарии не блокируют MVP.

## Контракты API и событий

Отдельные consumer-driven contract tests и автоматическая проверка совместимости Kafka JSON Schema в MVP не вводятся. Они становятся необходимыми при появлении внешних consumers или выделении модуля в отдельный сервис.

OpenAPI и JSON Schema остаются нормативными артефактами. Их синтаксис проверяется при изменении, а совместимость оценивается в review и integration-тестах затронутых модулей. Breaking changes требуют новой версии контракта и ADR либо явного плана миграции consumers.

## Security-тестирование

При каждом merge выполняются:

- unit- и integration-тесты аутентификации, ролей и object-level authorization;
- SAST, SCA и secret scanning;
- проверка зависимостей на запрещенные critical/high уязвимости;
- тесты безопасной конфигурации парсеров и ограничения файлов.

После сборки образа выполняются container scan и формирование SBOM. Перед выпуском в `production` выполняются DAST, негативные тесты REST/STOMP, набор вредоносных файлов и проверка основных security headers. Ручной security review проводится перед пилотной эксплуатацией и после значимых изменений аутентификации, авторизации или обработки файлов.

## Проверки pipeline

| Событие | Обязательные проверки |
|---|---|
| Локальная разработка | unit; integration по необходимости |
| Merge request | компиляция, static analysis, unit, integration, SAST, SCA, secret scanning |
| Merge в основную ветку | все проверки merge request, сборка и scan OCI-образов, развертывание и smoke E2E в `dev` |
| Выпуск в production | полный E2E, DAST, file-security regression, проверка миграций и ручное подтверждение |
| Расписание | полный E2E и расширенное сканирование зависимостей в `dev` |

Ошибка обязательной проверки блокирует merge или выпуск. Исключения для security findings документируются с владельцем, обоснованием и сроком пересмотра.

## Критерии готовности изменения

Изменение считается готовым, если:

- acceptance criteria выполнены;
- добавлены необходимые unit- и integration-тесты;
- затронутый E2E-сценарий обновлен;
- миграции проверены на чистой и существующей БД;
- ошибки и значимые ветви бизнес-правил проверены;
- документация API и архитектуры обновлена;
- обязательные проверки pipeline завершились успешно.

Формальный процент покрытия не устанавливается. Ответственность за достаточность тестов несут автор изменения и reviewer; отсутствие порога не является основанием оставлять критическую логику без тестов.

## Вне MVP

- нагрузочное и длительное soak-тестирование;
- chaos engineering;
- consumer-driven contract testing;
- автоматическое блокирование несовместимых изменений Kafka schemas;
- формальные mutation testing и coverage gates.

Нагрузочные испытания добавляются до масштабирования или после появления целевых показателей нагрузки и доступности.
